# Removing JkrAllocationDomain and JkrHeapRuntime

Read-only plan against the round20 allocation changes. No production edits, builds or tests. The remaining pair contains four separate responsibilities: physical process arenas, owning temporary solid heaps, borrowing manually destroyed original heaps, and scoped current-heap/routing restoration. Do not transplant these classes or their DomainRecord linked list to another directory.

## First remove dead users

`runtime/ScenarioCatalogOwnership.cpp/.hpp` and `ParticleResourceOwnership.cpp/.hpp` are now production-orphaned. Their only constructor callers are RuntimeContext's `initialize_scenario_catalog` and `initialize_particle_resources`; neither initializer, either retain getter, nor either active getter has a production caller. The only test references are always-null active-state assertions in RuntimeContextFailureTests. Delete these four files and the unused RuntimeContext includes/members/methods. Actual GameSystemSceneController/ScenarioDataParser and GameSystemObjHolder/ParticleResourceHolder already own the process resources. The round17 note identifying these as live production child-domain dependencies is now outdated.

GameResourceRuntime::create_cohort has only one caller, OriginalCameraContextTests. Replace that fixture allocation with an actual bounded child heap when migrating it; do not preserve a production cohort factory solely for the test.

## Actual SDK ownership contract

Use shared pointers to actual JKRHeap objects, with a weak self-handle on each actual heap, rather than shared pointers to a new Domain substitute. Proposed API spelling:

- `JKRHeap::retainNativeLifetime() -> std::shared_ptr<JKRHeap>`: under the existing SDK current-heap mutex, lock the actual heap's weak handle. For an original manually owned heap, create its borrow control block once, retaining the actual parent's handle. No global heap-to-owner lookup. Do not alias every child's pointer to the parent's shared control block: independent child control blocks are needed to detect retirement with child borrowers still live.
- `JKRHeap::retainCurrentNativeLifetime() -> std::shared_ptr<JKRHeap>`: observe the selected actual heap when client allocation context is active, including a nested HostAllocationScope. An absent client context returns empty, preserving existing fallback behavior. Retiring heaps reject a new lease. Aurora's callbackGuest routing bit covers the normal existing scope/callback cases; audit the remaining teardown/explicit override cases before deleting the old scope-depth TLS.
- Actual heap factory ownership, e.g. `JKRSolidHeap::createNativeOwned(size, parentHandle, errorFlag) -> std::shared_ptr<JKRSolidHeap>`, creates the ordinary solid heap and publishes its actual weak handle before exposure. A host-allocated shared control block retains the parent; its final deleter runs the actual destroy operation before releasing that parent. Initialization failure destroys the just-created child. No Game budget constants enter this SDK API.
- `JKRHeap::validateNativeRetirement()` / a retirement flag protect manually owned original heaps against live borrowed handles. Check before destruction mutates tree/disposer state. Shared-owner final deletion runs after its strong count reaches zero; original raw Game-owner destruction must reject live borrowers instead of deferring its original heap switch. Cover virtual do_destroy entry points, not only one convenience wrapper. Constructor/stack-backed SDK fixtures may retain an explicit manual owner contract.

Heap lifetime is not allocation lifetime: a token must not claim that bytes survive freeAll/freeTail. Preserve the existing disposer/finalizer/provenance behavior and actual FileLoader/ResourceHolderManager archive-borrow preflight. Blindly rejecting every freeAll while a heap token exists would break normal stationed-loader bulk reuse and heap-owned finalizers.

`JKRHeap::CurrentHeapScope` should retain both selected and previous actual heap handles. Restore the previous selection and unlock the current-heap mutex before releasing either handle, because their final release may retire callbacks. Keep routing explicit through Aurora ClientAllocationScope and HostAllocationScope; delete the compatibility host alias. Synchronous allocation call sites can use the canonical current scope plus explicit client routing. Existing worker waits must keep their present pattern: caller-selected heap and ClientAllocationScope without holding the SDK current-heap mutex over an OS queue, main-thread request, VI retrace or GX drain. MR::CurrentHeapRestorer should use the same actual selection/restoration lifetime rules without silently changing allocation routing.

## Process storage belongs to the current process owners

GameResourceRuntime should directly own root arena storage, root shared heap, MEM1 and embedded tables. Reuse round20's caller-owned JKRExpHeap::createRoot overload; give its shared actual-heap deleter the root allocation token so arena free occurs after root destruction. Store raw allocation ownership in standard shared_ptr<void> deleters, not another HeapRuntime class. Existing budget fields remain on GameResourceRuntime / callers.

Move the MEM2 preparation method onto GameResourceRuntime. Aurora continues to own binding validation/containment and ARAM retirement, while the process owns bytes. Original HeapMemoryWatcher::sRootHeapGDDR3 needs its actual owner handle to retain that MEM2 allocation plus its JKR parent. The root and GDDR3 handles must be weakly published on their actual heaps. MEM2 is installed after root creation, so capturing an initially empty MEM2 token in the root deleter is insufficient. The actual GDDR3 heap's owner is the correct place to retain its backing allocation.

OriginalProcess then borrows actual root/stationed heap handles. HeapMemoryWatcher owns its native root-GDDR3 handle and native destruction preflight while keeping the original heap sizes, hierarchy, creation timing and raw public fields. Its native cleanup must run before that handle's own storage/parent is recycled; the current OriginalProcess merely releases the HeapMemoryWatcher singleton and recursively destroys raw child heaps, so update this exact teardown path. Release Game/resource borrowers first, retire original child heaps in their existing order, then release physical backing. ARReset and MEM2 unbind remain outside the heap selection mutex.

## Practical coordinated lanes

1. **SDK lane:** JKRHeap.hpp/.cpp, JKRExpHeap.hpp/.cpp, JKRSolidHeap.hpp/.cpp and the other do_destroy providers as needed; actual weak handles, owned factories, retirement and retained CurrentHeapScope. Agree the shared-pointer API before callers migrate. No Game policy here.
2. **Process lane:** GameResourceRuntime.hpp/.cpp, HeapMemoryWatcher.hpp/.cpp, OriginalGameApplication.cpp, RuntimeContext.hpp/.cpp; direct arenas, root/GDDR3 ownership, dead scenario/particle providers, and actual original teardown. Also migrate OriginalDisplayLifetime and disabled-audio temporary heap creation to the real solid-heap factory if those paths remain; they still have live RuntimeContext constructors. MessageHolderOwnership.hpp has an unused JkrHeapRuntime forward declaration to delete.
3. **Resource/execution callers:** replace domain members/parameters with actual shared heap handles in ResourceHolder/LayoutHolder/ArchiveHolder/FileLoader/manager, ModelManager/MarioAnimator, Scene/SceneObjHolder/NameObjListExecutor/category callback retention, EffectSystem, CameraDirectorRuntime, SceneScheduler and typed resource codecs. Existing domain->heap() becomes dereference of the retained actual heap; preserve member destruction order and async scope boundaries. This touches 57 src files by current broad domain/scope/include search (18 contain allocation scopes; 35 contain the host alias), so avoid overlapping writers.
4. **Fixture/retirement lane:** minimally adapt existing heap/resource fixtures to actual roots/owned solid heaps; remove only obsolete Domain-specific contracts. Retain checks for parent survival, previous-current restoration, explicit external heaps, unwind and out-of-scope deletion. Remove the two compat files only after every consumer has moved; do not leave forwarding aliases.

A coherent full removal is larger than round20's operator move. The independent four-file orphan cleanup can land first. The main implementation can then proceed in one coordinated API migration with the parent's normal integrated build; this plan requests no additional test campaign.
