# Canonical JKernel allocation owner

Deleted `src/compat/MetrowerksAlignedNew.cpp` and `JkrAllocationRouting.hpp`. The complete 32 native allocation/deallocation overloads are now in the existing `JSystem/JKernel/JKRHeap.cpp`, the original donor owner of operator new/delete. Its anonymous helpers perform native host/client routing directly; there is no exported routing bridge or replacement provider file. The two routing functions and four duplicated arena-bound atomics were removed from JkrAllocationDomain.cpp.

The unchanged operator bodies preserve ordinary/array, C++ aligned, sized deletion, nothrow, original integer alignment, heap placement, constructor-failure deletion, new-handler retry, `INT_MIN` rejection, and negative tail alignment. Routing continues to use Aurora's existing thread-local allocation state. Explicit heaps still win over host escape scopes; ordinary allocation honors current Game selection under the same recursive SDK mutex. Signed-size limits and minimum pointer alignment remain unchanged. Host zero-sized allocation still requests one byte. Global delete consumes exact JKR provenance first, releases that registry lock before entering the owning heap, and otherwise frees host storage only after range checks.

Root storage construction now belongs to `JKRExpHeap::createRoot(void*, u32, bool)`. It validates caller-owned aligned storage, constructs the same expandable root/header layout, marks its memory externally owned, and publishes the original `JKRHeap::mUserRamStart/mUserRamEnd/mMemorySize` fields. The two pointer fields use atomic publication because global delete may run on native threads. No separate root-range registry or duplicate bound fields remain. The actual JKRHeap destructor clears root/current/system selection and the canonical root bounds after disposer/finalizer/allocation-record retirement. JkrHeapRuntime retains its existing budget validation, physical allocation, domain lifetime, and ARReset sequencing; it now calls actual heap construction/destruction instead of setting SDK internals itself. MEM2 unbinding is outside the current-heap lock because that SDK boundary may wait for callback retirement.

Aurora's existing MEM2 owner exposes `contains_mem2_address(const void*) noexcept`. It reads the actual bound-arena limits, not the mutable free-water marks. Existing bound limits are atomic; no mirrored range exists. The query is nonallocating and does not take the watermark mutex, avoiding allocator recursion/deadlock from exception cleanup while that mutex is held. Existing MEM2 validation, watermark locking and ARAM callback release remain in OSArena.cpp. Aurora has no JKR/Game dependency.

JKRHeap.hpp now declares the complete original heap/integer placement new/delete pairs, including array heap placement and constructor-failure deletes previously absent from that canonical header. Existing forced-prefix declarations remain identical; dismantling that unrelated prefix is a later task.
