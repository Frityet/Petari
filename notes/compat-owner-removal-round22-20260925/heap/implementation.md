# Actual JKR heap lifetime ownership

Five canonical JKernel files changed; no HeapMemoryWatcher change needed. Existing original heap factories and allocation/disposer algorithms remain in place. No registry, renamed domain object, or allocation-depth TLS was added.

`JKRHeap::Handle` is a shared pointer to the actual heap. Per-heap weak publication distinguishes manually destroyed Game heaps from explicitly adopted native roots/temporary heaps. Manual child handles retain their actual parent and do not delete the child. Root retention requires an explicit shared owner. Adoption permits only an unpublished live heap, retains parent/backing through complete original destruction, and keeps control-block allocation rollback outside the heap-selection lock. An expired adopted handle rejects new publication while its deleter runs. Adoption validation failure leaves the raw heap untouched; once shared ownership construction begins, allocation failure destroys the raw heap through that same deleter.

Owning and borrowing deleters move parent/backing captures into locals at final strong release; stale weak pointers therefore retain only empty control blocks. Root backing stays alive until the root destructor has cleared SDK global arena pointers. `bindNativeBackingStorage` attaches external byte ownership directly to an actual manually owned heap (MEM2 GDDR3); derived do_destroy methods detach this token into a local so its bytes remain valid through the complete destructor and parent deallocation.

`validateNativeRetirement` rejects live native handles and descendant borrows, and additionally requires a process root's actual child tree to be empty. `beginNativeRetirement` performs this preflight before disposers run and prevents new borrows. Exp/Solid/Unit virtual do_destroy paths use it; derived/base destructors also enforce the invariant for direct destruction. Backing-bound heaps require the complete destroy path so storage cannot release halfway through a base destructor. Native handles do not override original freeAll/freeTail semantics or archive borrow checks.

`CurrentHeapScope` retains the selected and previous actual heaps, restores the original pointer and unlocks before dropping either handle. Exception cleanup likewise unlocks before release. It does not alter client routing. `retainCurrentNativeLifetime` observes actual current selection only when Aurora callbackGuest is active, which survives HostAllocationScope. Original client entry/callback scopes provide routing; no extra TLS is needed. Deleter callbacks run under GuestThreadExecutionScope and explicit client routing, with no heap-selection mutex across original disposers/callback waits.

Integration: root/process lane creates and adopts the root using its allocated byte token; attach MEM2 token to HeapMemoryWatcher::sRootHeapGDDR3 immediately after original createRootHeap. Original raw child heaps are retired in the existing process postorder before the last root handle. Game/SDK callers migrate to Handle and CurrentHeapScope plus explicit ClientAllocationScope; host metadata uses Aurora HostAllocationScope directly. Retained raw Game heap handles must be released before original scene/game heap destruction; this is an explicit boundary rather than deferred Game destruction.

No builds, tests, staging or commits. Runtime retirement still awaits the parent integrated build and smoke.
