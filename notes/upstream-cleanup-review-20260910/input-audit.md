# WPad / GamePadUtil ownership review

Read-only audit of current sources on 2026-09-10. No source edits, builds, tests, or commits were performed. This review is limited to WPad, GamePadUtil, and the SDK input records they consume; it does not revisit working Mario movement or camera behavior.

## Current boundary

SDL keyboard/mouse events enter `AuroraWindow`, then `RuntimeContext::begin_frame` publishes buttons, pointer, analog stick, and swing into `aurora::WpadService` before camera/actor movement (`src/runtime/RuntimeContext.cpp:867–876`). This is appropriate native input adaptation and should remain outside Game.

Original Game input state is only partially used. `WPadOwnership::update_pointer_samples` reads KPAD and updates each actual WPad's pointer and button objects, while setting only `mIsConnected` directly (`src/compat/WPadOwnership.cpp:72–81`). Its owner is currently nested inside `StarPointerDepthOwnership`, and sample publication is triggered by that owner's update (`src/compat/StarPointerDepthOwnership.cpp:159–161`). Thus original input lifetime and projection are coupled to the pointer-depth owner instead of an original WPadHolder/system-input owner.

`src/Game/Util/GamePadUtil.cpp` exists but is excluded by `src/Game/xmake.lua:79`. Active `GamePadUtilCompat.cpp` reads original WPadPointer for pointing queries but reads Aurora directly for button, stick, swing, and connection queries. That bypass currently supplies working Mario input, but it leaves direct original WPad consumers with a different state surface.

## Concrete cleanup findings

1. **Game-facing wrappers duplicate original source.** `GamePadUtilCompat.cpp` reimplements original pointing forwards, core/sub button and trigger masks, player/system aliases, stick checks, camera-relative stick math, and WPad count/connection queries. Pointing wrappers already call the original Game record; they add no native behavior. Core button records also already receive the original update algorithm. These bodies belong in the original GamePadUtil implementation once its dependency cohort is complete. Do not simply remove the exclusion today: acceleration/swing methods and original extension records are not complete.

2. **Original methods are copied into compat.** `OriginalWPadRecords.cpp` contains WPad construction/accessors, WPadReadDataInfo construction/accessors, WPadButton construction/update, and several original child constructors. `OriginalWPadRumblePause.cpp` also contains recovered Game methods. Most of these are original algorithm bodies relocated into compat. Native lifetime ownership, exception cleanup, process-lifetime callback-table allocation, and Game heap retention are legitimate host responsibilities; they should remain in an owner/SDK boundary while original method definitions come from their reference files. Moving the entire current compat file into Game would also move its native cleanup policy and is not the proposed cleanup.

3. **Original input processing is skipped.** Original `WPad::update` invokes button, acceleration, pointer, swing, rumble, stick, leave-watcher, and info-checker in retail order (`decomp/src/Game/System/WPad.cpp:39–59`). Current ownership invokes pointer then button only. Original WPadPointer is already imported and used, so retain it. Original WPadAcceleration and WPadHVSwing recovery is incomplete; WPadLeaveWatcher::update is still absent in reference source. Full WPadHolder activation therefore needs a coherent recovered dependency cohort, not empty methods or selective flag writes.

4. **SDK KPAD data is incomplete.** Aurora's `KPADStatus` omits core acceleration magnitude/speed, device type, data format, and the extension union; its error field is s32 instead of the original s8 (`aurora/include/revolution.h:94–117` versus `decomp/libs/RVL_SDK/include/revolution/kpad.h:37–78`). `KPADRead` supplies only a single core/pointer sample and never publishes Aurora's existing `sub_stick` into an extension record (`aurora/lib/wpad.cpp:337–373`). The reference WPadStick requires `ex_status.fs.stick`, and `MR::isDeviceFreeStyle` requires `dev_type`. The complete original SDK declaration and meaningful native extension publication are prerequisites for retiring direct MR-to-Aurora stick access.

5. **Connection APIs are placeholders, with one wrong observable contract.** `WPADSetConnectCallback` and `WPADSetExtensionCallback` are no-ops (`aurora/lib/wpad.cpp:411–413`); no original connected/disconnected/extension callbacks update the Game record. Original holder setup also references allocator/init/sensor-position and info APIs absent from this Aurora surface. `WPADProbe` is currently declared BOOL and returns1 for connected and0 for disconnected (`aurora/include/revolution.h:123`, `aurora/lib/wpad.cpp:375–380`). The actual SDK declares s32 (`decomp/libs/RVL_SDK/include/revolution/wpad.h:419`), and original `getHBMKPadData` branches on `WPAD_ERR_NONE` (0), BUSY, and TRANSFER (`decomp/src/Game/System/WPadHolder.cpp:164–178`). The current result convention therefore reverses success and failure for original consumers. `tests/AuroraNativeTests.cpp:295–315` explicitly expects the wrong BOOL contract and must migrate with the SDK correction; it is not evidence of retail accuracy.

6. **Reference WPadStick cannot be imported unchanged yet.** Current `decomp/src/Game/System/WPadStick.cpp:23–38` reads `stickEx` and computes its difference from the previous stick, but never assigns `stickEx` into `mStick`. It then calculates current flags from unchanged `mStick`. Retail `WPadStick::update` explicitly stores current X and Y to offsets4 and8 at0x803ADEA0 and0x803ADEA4 before speed/edge publication (`notes/gateway-audit-20260907/restoration/retail/asm/Game/System/WPadStick.s:43–60`). This is a confirmed reference decompilation omission, not a native workaround opportunity. Recover it reference-first with Wii comparison before activating the original method. It does not explain current Mario motion because the active MR provider bypasses this record.

## Suggested coherent order

First correct the SDK record/probe/callback contracts and provide typed input ownership independent of star-pointer depth. Recover WPadStick's missing original store and the mandatory update helpers, then run original WPad/WPadHolder processing with real native KPAD samples. Retire direct GamePadUtilCompat providers in that same coherent migration and enable the original utility TU. Original source algorithms should not be rewritten into Aurora; Aurora should provide the SDL-to-SDK records, device capabilities, callback delivery, and native resource lifetimes that those algorithms require.

Preserve current original pointer-history behavior and actual heap/callback ownership checks. Validation for the eventual migration should exercise original WPadStick and WPadButton records from native samples, including signed/diagonal/neutral movement, threshold transitions, release, connection/extension transitions, and repeated owner teardown. Current live movement success establishes the active bypass path, not completion of the original-record migration. This audit makes no new runtime claims.
