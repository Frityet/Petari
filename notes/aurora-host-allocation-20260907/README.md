# Native allocation escape at Aurora resource boundaries, 2026-09-07

The scene scheduler now enters the actual original JKR domain while invoking original Game methods. This makes original ordinary `new` select that heap, including dynamic AutoEffectInfo allocation, but it also exposes any native C++ cache growth reached through those methods. Aurora GPU resources, FIFO processing, frame queues and texture caches must outlive an individual Game heap.

A reusable header, aurora/include/aurora/allocation.hpp, owns thread-local RoutingState with independent guest allocation and callback-caller flags. HostAllocationScope snapshots the whole state and disables guest routing while retaining the caller's callback flag. ClientAllocationScope restores that flag only during an actual synchronous callback, then restores the complete previous state. Neither class allocates. Worker threads start with default host state; this change does not capture a foreign heap or manufacture cross-thread Game ownership.

Root JkrAllocationDomain uses this same state instead of a private bool. Each explicit Game scope and original heap teardown saves/restores the full state. JkrHostAllocationScope is the Aurora scope alias. Allocation-scope and heap-teardown depth remain independently tracked, so current_jkr_allocation_domain still observes the selected original heap while inside a native host escape. Explicit JKR placement allocations still use their supplied heap, as before; host escapes affect ordinary routed new.

The guarded native owners are enumerated in surfaces.json. They include FIFO growth/publication/drain and command decoding; direct GX texture/display copies and readback; texture object/content caches and native texture creation; GPU bind-group/sampler caches; recording/staging/offscreens and frame lifetime; depth snapshot allocation/completion; and display-list optimization. No original actor, stage, Game draw or particle callback body is placed under a blanket host scope. Allocation-free GX register setters keep their existing fast path.

Actual callback sites restore caller allocation state narrowly: GX draw-done, registered custom graphics draw/encoder tasks and their completion callbacks, virtual texture readers, and frame-end callbacks. Internal WebGPU mapping callbacks remain native. No new thread/domain transfer is implied by callback registration. The original OS mutex path was audited: OSExecution uses an existing static CPU mutex/condition variable, intrusive SDK queues and an embedded thread_local OSThread initialized by field stores. It has no first-use STL registry allocation that would recursively invoke routed new through HeapLock.

All 13 changed native translation units initially passed LLVM23 syntax using their actual compilation database commands. Final integration and additional moved-input checks are recorded below once complete. This is allocation-boundary validation, not full Gateway gameplay completion.


Final allocation revision validation: scheduler heap routing, the 96-texel DirectDraw test, and the extended actual-disc effect test all built and exited0. The scheduler verifies nested Host/Client scopes, explicit nested original domains and exception restoration. Each of two original effect scenes generated7 JPA particles and9 GPU draws, with2,391,153 changed RGBA bytes. Creating64 tagged depth snapshots under the actual Game scope left Game heap free size unchanged; a following original new still selected Game, and retained native snapshot metadata remained accessible after scene heap retirement.

Retained input storage was audited too. Debug-label APIs now take string_view and copy into host-owned strings inside the guard. end_frame takes a callback reference and copy-captures its std::function wrapper under host routing. TextureUpload and palette-conversion requests contain GPU/TextureRef handles rather than movable STL buffers. Opaque client callback pointees retain the existing caller lifetime contract. The debug string path also passed a separate syntax check with AURORA_GFX_DEBUG_GROUPS enabled.
