# Original talk A-button gate audit

The current decompilation is faithful. No Game or decomp source changes are justified by this audit.

After reading `decomp/AGENT_DECOMP_GUIDE.md`, inspected retail `TalkStateEvent::talk`, `WPadButton::update`, both A predicates, and both MR wrappers. `retail-excerpts.s` retains the relevant assembly. Every instruction in these six functions was compared byte-for-byte against the currently available retail DOL; all match (`retail-verification.json`). At the time of this audit, the three native Game source files were byte-identical to decomp. The subsequent CP932 migration permits only its separately verified literal wrappers/includes.

At 0x802A2C18 the retail function calls held-A. The `beq` at 0x802A2C20 skips advancement when it is false. It calls trigger-A at 0x802A2C28, compares with zero, then uses `bne` at 0x802A2C30 to skip advancement when trigger is true. Only held-A true with trigger-A false reaches the assignments that set the latch `_1C` and the local advance flag. There is no missing negation or reversed branch.

The `_1C` latch starts true when the talk opens. While true it tracks held-A and suppresses advancement; a release clears it. When text is fully visible and that latch is clear, a new press has held=true/trigger=true and does not advance; a later held sample with trigger=false advances. Once advanced, the latch suppresses repeated pages until release. The `_10` counter is separately used for text skipping after a longer hold.

`WPadButton::testButtonA` loads the hold field at Wii offset 4. `testTriggerA` loads the trigger field at offset 8. Both extract bit 11 (mask 0x0800), matching both SDK and Aurora `WPAD_BUTTON_A`. `WPadButton::update` masks triggers against the prior hold and copies hold/release for status 0 or -2, matching the retail sequence. The MR wrappers get the specified WPad and call those exact methods.

Therefore a single held/trigger sample followed immediately by release cannot advance ordinary completed dialogue; this is original behavior. This audit does not establish whether a sustained physical key is sampled correctly by the native input path. That boundary needs separate observation. It is not grounds for changing the original dialogue debounce, extending short inputs specifically for dialogue, or claiming physical keyboard gameplay from a controller script.

## Shared debug controller scripts

Moved the existing button and pointer script parsing/application out of RuntimeContext into `src/runtime/DebugWpadInputScript.{cpp,hpp}`. Both the standalone RuntimeContext and OriginalGameApplication now use this one helper, under `#ifndef NDEBUG`. Existing button/pointer syntax and behavior are preserved: inclusive zero-based frame ranges, semicolon-separated entries, button masks OR with physical input, and the last active pointer span wins. Invalid existing button/pointer entries retain their previous ignored-entry behavior.

Added an explicit Nunchuk stick facility: `SMGPC_DEBUG_WPAD_STICK_SCRIPT=first-last:x:y;...`. Single frames and open-ended ranges also work; the last active span wins. Each axis must be finite and in [-1,1]. Invalid stick syntax/ranges/coordinates throw at configuration time. A zero vector is an explicit scripted center; outside spans physical input resumes. Example generic inputs are `SMGPC_DEBUG_WPAD_BUTTON_SCRIPT=20-25:A;40-45:B`, `SMGPC_DEBUG_WPAD_POINTER_SCRIPT=10-20:100,200,true`, and `SMGPC_DEBUG_WPAD_STICK_SCRIPT=50-80:0.5:-0.25`.

OriginalProcess applies the script to host button/pointer/stick values before publishing them to Aurora WpadService, before its normal GameSystem::frameLoop. The original update later calls GameSystemObjHolder::update, WPadHolder::update, KPADRead, then WPad::update. Frame index is the original loop's completed-frame count before increment, so the first sample is frame 0. No Game state, positions, stage logic, or dialogue fields are altered. The original application logs script configuration strings, counts, and activation transitions. RuntimeContext host-input traces include script provenance and raw/effective stick axes. Normal absent-script paths are unchanged; release builds contain no script parser or application.

Validation: `xmake build -j 8 smg-pc-frame-button-state-tests` and the resulting binary both passed (input-script-build.log, input-script-tests.log). Expanded the existing meaningful original WPad boundary test: valid/invalid range parsing, overflow rejection, inclusive endpoints, overlap, physical-button preservation, pointer precedence/invalidity, open-ended ranges, stick finite/range rejection, then a real WPadOwnership owner sampling scripted A through Aurora KPAD. It observes a single trigger, multiple non-trigger held frames, the normal release, physical B retained, and Nunchuk axes delivered to the actual KPAD record. This proves scripted-controller behavior, not physical keyboard gameplay. Native production build and clean original runtime validation are recorded separately.
