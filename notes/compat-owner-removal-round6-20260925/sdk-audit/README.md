# Round-six owner recommendation (read-only audit)

The three JPA providers and `J3DShapeMtxGameCompat.cpp` are original **Game/System/Overwrite.cpp** methods. Current decomp defines all of them. Do not move them into generic JParticle sources or replace their MR math calls: the game overrides intentionally use componentwise 0.001 normalization guards and the StripeX 0.01 fallback. Generic JPABaseShape line/stripe definitions differ. The DOL/compiler recovery evidence in `notes/original-jpa-draw-20260903` and `notes/original-jpa-overwrite-20260903` agrees with the current Game donor. This corrects the initial provisional SDK-only ownership interpretation.

Recommended closure: restore all 16 public JPA/shape methods and their private projection/direction/rotation/plane/list helpers and exact display lists into Game/System/Overwrite.cpp; delete all four compat providers. Keep mLastNonzeroUserWork reset on emitter reuse because EffectSystemOwnership callback retirement reads it. Keep contraction disabled. Existing canonical generic JPA and ShapeMtx files already exclude these overrides. Other Overwrite donor definitions have separate native canonical owners (heaps, streams, GX capture, audio, SDK matrices); inventory rather than duplicate them.

Tests: original-jpa-manager (all authored resources/CPU calculation and camera helper), original-particle-resource-owner, original-effect-ownership and an integrated real process teardown. The CPU manager does not call drawing and cannot prove GPU pixels; use actual process drawing for render evidence.

A separate small SDK follow-on is J3DMaterialLoaderFactoryCompat.cpp -> complete JSystem/J3DGraphLoader/J3DMaterialFactory.cpp. Both sides contain the same full method family. Differences are mostly spelling; retain native sizeof/uintptr_t behavior and inspect modifyPatchedCurrentMtx (native copies whole coord; donor assigns mInfo). Use material-resource, material-table and model-resource tests.

Defer J3DModelLoaderCompat.cpp/.hpp until coherent resource integration: the current 76-line provider has three public bounded wrappers and finalization only, while the 566-line donor owns full block read/construct paths. J3dModelResource presently constructs retained joint/geometry/material/texture owners itself, validates hierarchies and serialized lists, then calls compat::finalize_j3d_model. Full restoration needs a decoded block boundary, actual J3DJointFactory and v21 factory closure, and retained guest identity for material diff flags. Merely renaming the fragment is insufficient.

Nw4rFontCompat.cpp also needs a complete three-owner split (ut_Font, ut_ResFont, ut_ResFontBase) and native decoded structures: current ResFont directly inherits Font, while donor uses ResFontBase; retain bounded endian decode, source sheet lifetime and Font host generation observers. Nw4rLayoutRecordsCompat.cpp belongs to lyt_pane.cpp but carries layout synchronization/animation interception; restore the complete original Pane owner and reconcile those callbacks with layout/Nw4rLayoutRecords before removing it. Nw4rDiagnostics.cpp belongs to db_assert.cpp, but the current Panic exception behavior and original PPC stack/console/VPanic path require an explicit native diagnostics design; a rename is not full restoration.

No builds or production edits were made during this audit. The subsequent implementation authorization is recorded separately in ../sdk/.
