# Original model-manager owner boundary

This tranche restores root source and maps the next native ownership boundary. It does not activate ModelManager, replace MarioAnimator, change renderer behavior, or claim jumping/gameplay closure. The native model-resource checkpoint is `d0617b1bc`; ResourceHolder migration is separate, concurrent parent/agent work.

## Root recovery and evidence

`src/Game/LiveActor/DisplayListMaker.cpp` now supplies every method directly needed by the existing complete ModelManager, plus their diff/inspection helpers. The only still-missing method in that class is the unrelated `addMirrorReflectionMtxSetter`. Five existing maker methods are preserved. `AnmPlayerBase::isStop()` is restored in its own root animation TU.

The original maker constructor allocates two `u32[materialCount]` arrays and a `4 * materialCount`-entry controller vector. Its root header incorrectly described the flag-array pointers as scalar `u32`; that is corrected. The retained resource pointer is const. A concrete root declaration for `MarioShadowProjmapMtxSetter` supplies the required original 0x10-byte derived type: its only extra field is a `ProjmapEffectMtxSetter*` at 0xC. The original constructor's store at `0x80168374` and vtable at `0x80587E0C` prove that field and override. Its constructor/update bodies remain a separate required source recovery; no body was invented to satisfy linking.

Reproduce:

```sh
python3 pc-port/notes/original-model-manager-owner-20260903/verify-source.py
```

The script compiles the two complete root TUs with configured GC3.0a3 Game flags and the Shift-JIS wrapper, splits verified RMGK01 retail DOL, compares objdiff output, and verifies all instruction operands and relocations. Output objects, commands, compiler logs and full diffs are under `build/original-model-manager-owner-20260903/`; the checked-in `source-evidence.json` records source hashes and results. DOL SHA1 is `25c5959534b3c21246c6c7e42021b916b41fb578`.

There are 25 newly restored functions and 30 verified functions including the five existing maker methods. Twenty-eight functions have byte-identical code after resolving real relocations. The view-projection inspection has only a bijective r30/r31 allocation exchange (99.17% objdiff). The animation stop query has two equivalent Boolean materializations (94.63%); the verifier checks the full instruction prefixes and all 512 resource-null/state-byte combinations, then checks its exact rate load, float equality comparison and return. The eight 98.33% flag wrappers differ only in empty-string relocation naming; their resolved bytes are identical. No branches or calls are discarded to obtain these results.

Source semantics preserved:

- `isValidDiff()` returns true in retail. `diff()` gates each material on its current flags but passes the union of program flags and ResourceHolder's MaterialAnmBuffer flags to the original virtual material `diff`. It selects the corresponding actual `J3DMatPacket` and preserves the per-material `ProhibitSchedulerAndInterrupts(false)` scope.
- `newDifferedDisplayList()` first inspects materials, then allocates each corresponding actual shape packet's diff buffer only if its union flag is nonzero. The constructor itself does not inspect textures or create controllers.
- `checkMaterial()` checks textures first, marks non-normal texture matrices with `0x200`, then adds one view-projection controller if any used texture-matrix slot has `(mInfo & 0x3f) == 9`. It scans all eight slots for every material and returns after the first qualifying controller.
- Texture eligibility checks exact authored names `IndDummy` and `ShadowDummy`; actual replacement checks `IndDummy` and `ShadowProjDummy`. This difference is present in retail and retained. Affected materials get `0x04020000`. The screen/shadow texture is copied through original `J3DTexture::setResTIMG`, preserving relative-pointer rebasing. Only one Mario shadow projection controller is added per texture inspection.
- BPK/BTP/BTK/BRK current flags delegate to the existing original MaterialAnmBuffer flag helpers with the original empty-name argument. There is no actor-name predicate or native-animation substitute.
- `AnmPlayerBase::isStop()` is true for an absent animation, state bit 0 set, or zero frame rate. The last comparison is a float equality: both signed zeros stop; a nonzero or NaN rate alone does not. The original call site emits this helper in ModelManager's retail object; its restored definition belongs to AnmPlayer.cpp.

## Current ownership map

The root ModelManager is already complete. Root J3DModelX also now has its constructor and view/draw lifecycle; the PC mirror is explicitly excluded by Game/xmake.lua. Older notes that list these bodies, XanimePlayer, J3DModel, or MtxBuffer as absent are outdated.

The currently available native SDK foundation includes complete typed model resources (INF/JNT/EVP/DRW/VTX/SHP/MAT/MDL/TEX), original J3DModel/ModelData/packet/matrix-buffer providers, and actual XanimeResourceTable, XanimePlayer and XanimeCore. `J3dModelResource` retains raw/native component storage and an original allocation domain; SDK load returns are borrowed from that owner. The legacy global ResourceHolder in ResourceHolderCompat.hpp is still a different class layout at this audit point. The concurrent migration must make every Game consumer and resource service refer to the same real Game ResourceHolder before ModelManager is published.

Today ActorRuntimeRegistry owns a native LiveActorModel and separate BCK/BRK frame controllers. `LiveActor::initModelManagerWithAnm` constructs that native wrapper and leaves the original `mModelManager` null. LiveActorModel owns J3dModelRenderer; that renderer constructs a private OriginalJ3dJointTree and recalculates it separately for drawing, joint lookup and bounds. Those are genuine SDK calculations but they are not the actual ModelManager/MarioAnimator model. MarioAnimator's PC initializer likewise leaves its resource/lower/upper player pointers null and selects native Wait/Run instead.

The original ownership/call sequence is different:

1. ModelManager retains model and optional separate animation ResourceHolders. `initModelAndAnimation` constructs the original model alone when there are no BCK resources, otherwise constructs its actual XanimeResourceTable/player/model. `MR::newJ3DModel` retains the original choice of J3DModelX for Mario and the existing root list of specialized models. That original choice must not be replaced with a plain J3DModel merely to avoid dependencies.
2. ModelManager creates actual visibility/material players from typed resource tables and actual model data. MaterialAnmBuffer supplies real material-animation attachment storage. Flags select shared/differed display-list ownership exactly as root `init` specifies; `isExistDiffMaterial` is called unconditionally even when there are no material-animation resources.
3. Original LiveActor movement calls ModelManager::update before actor control. This advances its Xanime player and material/visibility controllers once per logical game tick. Original calcAnmMtx writes the independent model base scale, calls the actor's original base-TR calculation, and calls ModelManager::calcAnim. The view phase calls actual ModelManager::calcView under the original `mIsNoCalcView` gate.
4. Original MarioAnimator replaces the manager's generic lower XanimePlayer with its authored-table player on the same actual J3DModel; its upper player also uses that model and shares the lower Core's joint-transform array. Its calc installs the lower/upper calculators at original joint boundaries and calls the actual model twice with Core modes 1 then 2. The old generic player and the replacement must not independently own/delete their shared model. The original scene heap's lifetime must be represented by an explicit native allocation owner.
5. Renderer submission and joint getters must borrow that exact model's matrices after the original calculation phase, never independently resample a BCK or re-run a private Core. The model's animation matrices already include original base TR/scale; concatenating actor TR again would double-transform them. View-dependent draw, normal, envelope and billboard matrices must also come from the same model's actual MtxBuffer. Original material-animation results, packet visibility and dynamic display lists cannot be observed by continuing to use immutable parsed material summaries alone.

## Native import and source blockers

The next coherent bounded import is complete original ModelManager plus its actual animation/material dependencies, first tested on retained complete typed resources and actual J3DModel instances before connecting actor runtime. This audit made no native production edits.

- AnmPlayerBase/MaterialAnmPlayerBase implementation and BtkPlayer/BrkPlayer/BtpPlayer/BpkPlayer/BvaPlayer headers/bodies are absent natively; their root bodies now exist, including the stop query restored here. They use actual animation resource objects, not source bytes cast as J3DAnmBase.
- Native J3DMaterialTable's animator entry/remove methods are declarations only. Their root implementations in J3DMaterialAttach.cpp exist and are needed for the material players' beginDiff/endDiff. The ResourceHolder migration does not own this import.
- DisplayListMaker now has the source needed by ModelManager, but actual MaterialCtrl virtual-body closure is not complete: base updateMaterial; FogCtrl constructor/update; ViewProjmapEffectMtxSetter constructor/update; MarioShadowProjmapMtxSetter constructor/update; and TexMtxCtrl constructors/operations remain root gaps or unavailable providers. These cannot be satisfied with empty virtuals. ProjmapEffectMtxSetter root bodies exist, but its root header still uses an opaque array while the bodies name UpdateEffectMtxInfo, mBaseMtx and other real fields: repair the typed declaration from retail before importing that TU. MirrorReflection controller is additional optional material functionality, not a reason to bypass actual flags.
- MR::newJ3DModel/newXanimePlayer/newXanimeResourceTable and actual model getter/base-matrix APIs require source-backed native providers. Existing actor-registry versions must be retired as ownership switches, including separate controller advancement. Model data is shared mutable original state, so original mutex/callback/calculator serialization and owner lifetime must encompass both Game evaluation and renderer snapshotting.
- Full J3DModelX import needs mechanical 64-bit pointer corrections for fields currently declared u32 but used as callback/model/display-list addresses; preserve original flags and dynamic class. The unusual root `viewCalc3` nonnull-matrix expression takes `&mtx` before reinterpreting. This is present in retail: `0x802A6B88` stores the incoming r5 at stack+8 and `0x802A6BCC` passes that stack address in r6 to calcDrawMtx. It is not a proven decomp error and must not be changed to dereference the supplied matrix as an assumed fix. Native 64-bit pointer/stack handling or proven reachability of this branch requires a separate architecture review. The raw disassembly is `build/original-model-manager-owner-20260903/modelx_view_calc3.asm`, and the verifier asserts these exact original instructions. MarioAnimator::calc also contains a literal J3DJoint +0x54 access that must become the actual typed field on native 64-bit builds.

## Required real scene resources

RuntimeContext already creates a real JUTVideo/WiiVideoService and then CaptureScreenDirector with its real capture texture before actor model initialization. J3DModelX's constructor unconditionally queries the current screen width, EFB height and screen ResTIMG to build its GD texture list; a bare CPU fixture without those owners cannot construct it honestly. The real current JKR heap/allocation domain, original GD scheduler/interrupt scope, original matrix globals and shape-packet user data must also be initialized. Preserve/restore ambient GD/J3DSys state at the native owner boundary as needed; do not alter Game algorithms to avoid it.

The shadow resource has a separate actual owner. `CollisionShadow::initCaptureTex` in root MarioShadow.cpp uses SceneHeapGDDR3 to allocate a 160x160 GX_TF_I8 JUTTexture, zeros its pixels, publishes it via MR::setMarioShadowTex, and sets clamp/linear sampling. Root `MarioActor::init2` constructs CollisionShadow after initDrawAndModel and MarioAnimator. That original order is significant: do not eagerly request a shadow replacement for a model whose initialization previously did not require it. The smallest valid shadow construction path is the real CollisionShadow constructor/texture lifecycle plus original DrawUtil shadow globals/getters/setters; drawing later requires its actual collision/volume and capture methods as well. A dummy texture, null-return provider, or static all-white image would not close this dependency.
