# Original Game execution character set

The native JMapInfo::getStringValueByHash caches BcsvTable::get_string verbatim. BcsvTable reads the original null-terminated bytes and does not call decode_cp932. Actual Game resource names therefore remain original CP932 bytes. The TextEncoding header comment describes a convention for selected native consumers, not a universal conversion performed by JMap.

Root Game source files are UTF-8 on disk, while the original sjiswrap compiler path encodes ordinary source literals to CP932. Clang emits ordinary Japanese literals as UTF-8. Its -fexec-charset=CP932 option is rejected; compiler-probe.cpp and clang-exec-charset.log preserve the check. Original MarioActor::isCommonEffect/isMaterialEffect check the CP932 prefixes 8B A4 and 91 AE; leaving these bodies unchanged requires matching execution-literal encoding. Common/material effect aliases also use byte offsets and original hashes.

Planned general boundary: generate compiler-only views of original Game ordinary narrow literals encoded as fixed-width byte escapes, while retaining editable Game sources and original source locations. Keep wide/UTF literal kinds distinct, comments and identifiers intact, and original resource bytes unchanged. A compiler VFS overlay could preserve original include/debug/dependency paths. This is not active yet; literal tokenization and build invalidation must be tested before integration.

Native service/UI text remains UTF-8 where it already uses that contract. Audit each existing decode_cp932 consumer before activation: ActorShadowCsvCompat, light/LightData, native EventCamera, StagePlacementResolver, DemoSheetRuntime, ObjectNameTable and PlanetMapCatalog. Any value passed back into Game must retain original byte identity; display strings should decode explicitly at presentation boundaries. In particular original NameObj names flow into SceneScheduler trace strings and JSON, where raw CP932 cannot be treated as UTF-8. Do not add UTF-8 alternatives just to the two Mario prefix methods.
